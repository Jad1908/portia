Write what you know about a table into the catalog: a prose summary, a role per
column, or a note. Judgment only. It never changes a measured fact.

Three fields, any combination:

- 'summary' says what the table IS, in the project's own words. One paragraph. A
  later call replaces it whole, so write the whole read, not an addendum.
- 'roles' maps a column name to what it is for: identifier, measure, timestamp,
  category, free_text, or a word of your own the project uses.
- 'note' is one sentence appended to what is known about this table, dated, kept
  in the order it was learned, never rewritten. Use it mid-chat, the moment you
  learn something a person building on this table has to know first: "outcome is
  a letter grade, not pass/fail", "License # 0 is 102 different businesses",
  "amount is net of tax". A note is not a finding: a finding rests on a query and
  a note rests on a read.

WORKS ON A MODEL TOO, by its name. A table you built with `record_step` has its
facts measured the moment a step is recorded, and no summary, because nobody has
read it yet. You just built it, so you are the one who can say what it is for.
Write that read before you build on it, or the next session reverse-engineers the
spec to find out.

When to call it: during indexing, for the summary and the roles; and in any chat,
for a note, as soon as you know the sentence. Do not wait to be asked and do not
save it for the end. What you learned and did not write down is gone when the
window closes, and the next chat repeats your mistake with confidence.
